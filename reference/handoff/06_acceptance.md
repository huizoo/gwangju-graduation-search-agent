# 검증과 완료 기준 4.0

## 1 검증 수준과 우선순위

이 패키지의 계약·참조 판정 검사는 문서와 예시 및 특정 규칙의 일관성을 확인한다. 실제 앱의 웹 수집·기관별 Agent·DB 재시작·정확한 일정 확보를 증명하지 않는다. 과거 probe도 사람이 고른 URL/사례의 개별 작업이며 전체 자동화 시험이 아니다. 실제 구현, fixture 검사와 실연동 증거를 별도로 기록한다.

먼저 다음 연결을 검증한다.

1. **날짜를 모르는 기관 탐색:** 기관 식별자와 목표 기간만 제공하고 정답 날짜/URL을 숨긴다. 인증 NEIS의 전체 기간/페이지 및 실제 앱 SearchProvider로 찾는지 확인한다. 알려진 날짜나 URL을 넣은 경우 seeded_date/seeded_url로 따로 기록한다.
2. **관측 오류 차단:** 잘못된 기관·게시물 부재·다른 연도/행사·정밀도 모순·없는 시각·입장/대여/하교 시각·합성 인용을 원문과 연결해 거절/보류시킨다. 단순 Schema 통과를 사실 검증으로 계산하지 않는다.
3. **정상 결과 제공:** 근거가 있는 날짜+시간, 날짜만, 실제 확인시점과 최신 fingerprint를 갖춘 정당한 수기 재확인을 통과시킨다. API·일반/판매 화면·HTML·지표가 같은 Publication을 사용하는지 확인한다. 모든 결과를 보류하면 실패다.

규칙별 양성·음성 시험 뒤 운영 허용 목록에 ID·버전을 등록한다. 초기 허용 목록이 비어 있는 것은 안전한 시작값이지 기능 완료가 아니다. 참조 검사에 활성화한 가상 규칙을 실제 자료원 검증 없이 운영에 복사하지 않는다.

최소 대표 기관 시험은 10개 기관을 목표로 초/중/고·유치원·어린이집·대학/전문대학·특수/기타 학교의 조건을 포함한다. 자료 접근과 일정 공개 여부에 따라 확보한 표본 범위를 그대로 보고하고 미시험 유형을 감추지 않는다. URL 10개와 기관 10곳을 혼동하지 않는다. 전체 목록 확보와 대표 표본 시험도 다른 완료 항목이다. 현재 시즌 공지가 없으면 과거 원문으로 parser/오류 차단을 검사하되 올해 일정으로 게시하지 않는다.

각 시험에 evidence_level, discovery_mode, source_origin, 기관/시즌, 원문 hash/위치, 읽기 범위, provider/모델의 실제 요청 설정, 외부 전송 범위, 기대값과 필드별 결과를 남긴다. URL·문서·기관·행사·모델 시도의 분모를 구분한다. 초기 8건과 재시도 4건은 일부 같은 사례/달라진 조건이므로 일반 정확도나 공식 성능 비교로 합치지 않는다.

## 2 게시 판정의 핵심 반례와 정상 사례

| ID | 입력/상황 | 기대 결과 |
| --- | --- | --- |
| P01 | 기관·시즌·실제 행사 식별이 해결되지 않았지만 다른 필드는 형식상 정상 | 행사 전체 일반 게시·현재 사용 보류 |
| P02 | 미해결 공식 취소 주의와 기존 수기 예정값이 함께 있음 | 기록 보존, 예정 표와 판매 목록 보류. 읽음만으로 복구 불가 |
| P03 | 수기 충돌 해결 주장에 confirmed_at·근거 메모가 없거나 예전 fingerprint | 관리 보존, 해결 불인정. 입력시점 대입 금지 |
| P04 | 검증된 장소와 다른 장소를 Publication에 넣으려 함 | 거절 또는 확인값에서 재계산. 최종 값 변조 허용 금지 |
| P05 | 유효한 공식 원문·등록된 규칙 ID/버전·필드/관측/hash 연결의 날짜+시작 시간 | 일반 date_and_time, current_date/time 허용, sales_ready=true |
| P06 | 날짜만 유효하고 시작 시간 없음 | 일반 date_only, 날짜 현재 허용, 시간 null, sales_ready=false |
| P07 | 실제 방법/시점/근거와 현재 fingerprint를 가진 정당한 직접 재확인 | 해당 충돌 해결 후 단일 판정 재계산 |
| P08 | 시간만 충돌, 날짜는 독립적으로 정상 | 날짜 유지, 시간만 보류. event.review_required만으로 전체 차단 금지 |

이 네 반례와 정상 사례는 계약의 입력·서버 판정·최종 출력 경로에 함께 적용한다. JSON 예제만 별도로 거절하고 앱이나 HTML은 우회하는 구현을 허용하지 않는다. 장소를 포함한 출력은 확인값에서 생성한다.

`checks/check_configuration.py`는 병합과 선택 설정의 사양 참조 검사다. 실제 SDK 초기화·호출, 비활성 백엔드 무접속, 앱 재시작·작업 snapshot·시즌 보존과 비밀값 비노출은 앱 구현 후 별도로 검증한다. 참조 검사를 실제 모델 연결 성공으로 보고하지 않는다.

참조 검사에서 다루는 범위와 실제 구현 후 자동화할 범위를 검사 결과에 구분한다. JSON Schema·참조 판정·SQL·API 참조 검사는 앱의 영속성과 네트워크 성공을 대신하지 않는다. 구현 단계에는 실제 요청/응답 계약, 데이터 참조·직렬화·env/defaults 연결, DB 재시작과 상태 전이를 추가한다.

## 4 실제 종단 시험

앱에 실제 연결된 NEIS/SearchProvider/reader/MCP를 사용한다. Codex 자체 검색이나 별도 브라우저 결과를 앱의 성과로 계산하지 않는다. 공식 API 인증·전체 기간·페이징을 확인하고 원문의 기관/행사/날짜/시간과 실제 인용 존재·의미 지원을 사람이 별도로 라벨링한다.

표본마다 일반 날짜/시간 표시, 현재 날짜/시간 허용, 판매 준비 여부, 수기 확인 필요와 이유를 기록한다. 현재 허용 날짜 기관 수·시간 기관 수·수기 필요 수를 분리하고, 전부 보류가 아닌 유용한 양성을 확인한다. 발견되지 않은 정답을 알 수 없는 표본에서 발견율 100%를 만들지 않는다. 정답이 있는 고정 표본의 누락과 잘못된 확정을 함께 보고한다. 인터넷 전체 무오류는 보장하지 않는다.

어머니의 기록 한 건을 입력해 재조사·동시 수정·새로고침·프로그램 재시작 후 보호를 확인한다. 실제 confirmed_at 없는 경우의 제한도 확인한다. 짧은 구간 한도로 멈춤/재개하고 cancel 직후 강제 재시작해 취소 보존을 확인한다. 종료 이후 늦은 응답과 사용량 예약을 검사한다. 전체 대상은 목록 마지막 페이지까지 포함해야 한다.

읽기용 HTML은 서버·인터넷 없이 열어 일반 조회의 확인시점/재확인 실패와 판매 필터가 같은 결과인지 검사한다. 악성 문자열의 실행 차단과 자체 검색·필터를 실제 브라우저에서 확인한다. 고정 fixture와 live는 데이터/화면/보고서에서 구분한다.

## 5 완료 게이트와 증빙 범위

| 완료 항목 | 필요한 증거 |
| --- | --- |
| 명세·참조 검사 완료 | 계약/예시/DB/API 참조와 단일 판정의 양성·반례가 일관됨. 실제 앱 완료와 구분 |
| P0 기능 완료 | 입력·저장·조회·조사·서버 검증·Publication·작업 재개/취소·HTML의 실제 끝까지 동작 |
| 자료원 실연동 완료 | 해당 자료원의 실제 인증/요청/응답·페이징·원문 및 필드 결과 대조 |
| 전체 목록 확보 완료 | 모든 대상 유형×5구 공식 범위의 출처·기준일·완전성/대상 0건 근거 |

완료 항목을 서로 대체하지 않는다. 모든 일정이 공개돼야 P0가 통과하는 것은 아니지만 미해결 기관·미확보 목록·미시험 자료원을 정확히 표시해야 한다. 규칙을 쓰지 않거나 모두 보류해서 오류만 줄이는 것도 핵심 수집 목표의 완료가 아니다. 실제 PC 배포·Windows 실행파일·예약 운영은 별도 범위다.

개발 증빙은 기능 완성도, 실제 기술의 역할, 한계·트레이드오프 세 항목에 맞춘다. PPT 작성·발표 준비와 별도 발표 증빙은 사용자가 별도로 수행하며 P0 완료 게이트에 넣지 않는다. Before/After 보너스 비교를 위한 추가 시스템도 만들지 않는다. 기본 품질 확인에 필요한 근거·사용량·오류 기록은 유지한다.

## 6 통과 후에도 남는 한계

고정 반례를 차단하고 정상 예제를 게시했다는 증거는 해당 범위에 한정된다. 모든 공식 원문의 정확성, 미공개 일정 확보, 이후 변경 부재, 전체 기관 수집률과 모델 일반 정확도를 보장하지 않는다. 보수적인 현재 사용 보류는 올바른 일정도 판매 목록에서 제외할 수 있고, 일반 조회의 과거 확인값은 최신 사실 보장이 아니다. 확인시점·범위·실패 사유를 항상 표시한다. 반복 실행·전체 비용·처리시간·배포환경은 실제 측정한 경우에만 성과로 보고한다.
