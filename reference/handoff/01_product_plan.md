# 기획안 4.0

## 1 목적과 대상

어머니가 꽃다발 판매 준비를 위해 기관마다 졸업식 날짜와 실제 시작 시간을 검색하고 메모하는 일을 줄인다. Agent가 공개 자료를 조사하고, 근거로 확인한 값과 추가 확인이 필요한 항목을 구분해 제공한다. 공개되지 않은 일정을 만들어 채우지 않는다.

대상 지역은 **광주광역시의 동구, 서구, 남구, 북구, 광산구**다. 실제 소재지와 공식 식별자를 함께 대조하며, 이름에 광주가 들어가는 다른 지역과 광주 밖 대학 캠퍼스를 자동 포함하지 않는다.

대상은 어린이집, 유치원, 초등학교, 중학교, 고등학교, 특수학교와 공식 목록의 기타 학교, 대학교와 전문대학의 광주 소재 캠퍼스다. 병설유치원과 초등학교는 별도 기관이다. 대학원과 학과는 소속 캠퍼스 아래의 행사 대상으로 관리하고 공시 레코드마다 기관을 중복 생성하지 않는다. 사설 학원, 교습소와 일반 평생교육 강좌는 범위에서 제외한다. 알 수 없는 기관 유형을 기존 유형으로 조용히 바꾸지 않는다.

전체 기관은 유형별 공식 목록을 확보해 관리한다. API 승인이 늦으면 같은 범위를 담은 공식 파일을 적재한다. 일부 관심 기관만으로 전체 목록 확보가 완료됐다고 표시하지 않는다. 공식 파일도 없는 유형은 `목록 확보 필요`로 남긴다. 접근 실패 때문에 대상 유형 자체를 서비스 범위에서 지우지 않는다.

## 2 시즌과 정보의 정밀도

새 시즌을 처음 만들 때의 학년도·탐색 기간·내보내기 키 기본값은 `config/defaults.json`에서 가져온다. 생성한 시즌과 화면의 선택은 SQLite에서 관리하며 프로그램을 다시 실행할 때 설정 파일로 덮어쓰지 않는다. 사용자가 화면에서 학년도와 기간을 선택·수정하며 `.env`에 매번 입력하지 않는다. 학년도와 실제 행사일은 별도 값이다. 겨울 시즌과 대학의 여름 졸업 시즌을 독립적으로 관리할 수 있다. 기간 밖 공지는 후보로 보존하고 범위를 넓히기 전 해당 시즌의 일반 일정표와 판매 준비 목록에 넣지 않는다.

전년도 기관과 공식 홈페이지는 재사용할 수 있다. 전년도 날짜나 시간을 올해 일정으로 복사하거나 매년 같을 것이라고 예측하지 않는다. 공지가 아직 없는 것, 검색으로 찾지 못한 것, 접근 오류와 명시적 미개최는 다른 상태다.

날짜는 일 단위·월 단위·미확인으로 구분한다. `2027년 2월 예정`은 월 계획으로 보관하며 임의의 날짜를 채우지 않는다. 수기 입력과 조회도 같은 정밀도를 사용한다. 실제 행사 시작 시각은 별도 항목이며 등교·입장·학위복 대여·하교 시각을 대신 넣지 않는다.

## 3 하나의 판정과 세 가지 조회 목적

서버의 `calculate_publication(event, season, validated_context) → Publication` 결과를 API, 화면, HTML 내보내기와 집계가 공유한다. 화면마다 다른 확인 규칙을 만들지 않는다. 계약의 구체 필드와 조건은 `contracts/README.md`를 기준으로 한다.

| 조회 목적 | 보여 주는 내용 | 사용 조건 |
| --- | --- | --- |
| 일반 일정표 | 정당하게 확인했던 일 단위 날짜와 연결된 시작 시간, 확인 방법·시점과 재확인 상태 | 원문 재확인에 실패해도 기존 근거가 여전히 유효하면 과거 확인값을 남기고 실패 표시. 현재 판매에 사용 가능한지는 따로 표시 |
| 판매 준비 목록 | 현재 사용 조건을 충족한 일 단위 날짜와 같은 행사·날짜의 실제 시작 시간 | `sales_ready=true`만 포함. 날짜만 확인됐거나 시간·날짜 재확인 실패가 해결되지 않았으면 제외 |
| 관리 기록 | 추출 후보, 월 계획, 확인일 미상 메모, 보류·기각 근거와 변경 이력 | 저장 사실과 확인 사실을 구분. 후보를 정상 확인값처럼 표시하지 않음 |

`Publication.calendar_*`는 일반 일정표에 허용된 값이며 판매 허용을 뜻하지 않는다. 판매 준비 여부는 같은 판정의 `sales_ready`와 필드별 현재 사용 허용으로 결정한다. 관리 기록의 `effective_value`나 모델 후보를 일반 일정표에 직접 복사하지 않는다.

원문 재접속 실패는 일정이 틀렸다는 증거가 아니다. 해당 값의 필요한 근거를 실제로 재확인하다 실패했고 유효한 대체 근거나 사람의 재확인이 없다면, 과거 확인값과 확인시점을 일반 조회에 남기되 해당 필드의 현재 사용을 보류한다. 조사하지 않은 경우, 보조 검색 실패, 오프라인 HTML 열람과 대체 근거가 충분한 한 출처의 실패를 같은 상태로 처리하지 않는다.

반대로 잘못된 기관이나 합성 인용 등 **기존 근거 자체가 잘못됐음이 밝혀지면**, 해당 관측을 기각하고 의존하는 판정을 다시 계산한다. 다른 유효 근거가 없는 값은 일반 일정표에서도 정상 확인값으로 유지하지 않는다. 관리 이력은 보존한다.

## 4 사용 흐름과 화면

1. 프로그램을 열면 저장된 일반 일정표가 열린다. 키나 인터넷이 없어도 저장 기록 조회와 직접 입력을 사용할 수 있다.
2. 학년도와 기간을 선택하고 유형별 전체 기관 목록의 확보 현황을 확인한다.
3. `전체 기관 조사` 또는 선택 기관의 `다시 확인`을 누른다. 대상 수, 이번 실행 한도와 연결 상태를 확인하고 시작한다.
4. 조사 중에도 기록을 조회·수정한다. `잠시 멈춤` 후 같은 작업을 이어갈 수 있다. 브라우저를 닫아도 서버가 실행 중이면 조사는 계속된다.
5. `확인할 목록`에서 필요한 정보와 연락처·원문을 확인하고 전화나 문서 직접 확인 결과를 입력한다.
6. 판매 준비 목록에서 날짜와 시간이 모두 현재 사용 가능한 일정을 보고, 같은 판정 결과를 읽기용 HTML로 저장한다.

| 화면 | 필수 내용과 동작 |
| --- | --- |
| 일반 일정표 | 날짜별·시간순, 날짜/시간 각각의 확인 방법과 시점, 재확인 실패 표시와 판매 가능 여부 |
| 판매 준비 목록 | `sales_ready=true` 필터. 실제 사용 판단에 필요한 근거·확인시점 표시 |
| 확인할 목록 | 행사 0건 기관 포함, 날짜/시간 누락·충돌·접근 실패 사유, 전화번호 복사와 원문 열기 |
| 관리 기록·상세 | 월 계획·추출 후보·수기 기록·기각 이력, 복수 행사, 필드별 근거와 변경 이력 |
| 기관 | 유형/구/이름 필터, 공식 목록 출처·기준일·완전성, 단건 추가와 연락처 정정 |
| 조사 현황 | 전체 대상/진행/남음/오류, 사용량, 멈춤/재개/취소, 설정 누락 안내 |

버튼과 표를 기본으로 하고 채팅 입력을 필수로 요구하지 않는다. 내부 도구 이름과 JSON 등은 일반 사용자 화면에 노출하지 않는다. 기본 글자는 16px 이상, 주요 버튼 클릭 영역은 44px 이상이다. 상태를 색과 글자로 함께 표시하고 이름·구·유형·날짜·확인 필요 필터를 제공한다. 날짜가 없는 행을 임의의 날에 배치하지 않는다.

## 5 직접 확인과 보호

직접 입력은 기관·시즌·행사 대상·날짜 정밀도·시간·확인 방법을 받는다. 기존 행사 보완과 새 행사 추가를 구분한다. 날짜만 또는 시간만 보완할 수 있지만, 시간의 일반 일정표 표시는 확인된 일 단위 날짜와의 연결이 필요하다.

전화·문서 직접 확인은 확인 방법과 실제 확인시점이 있어야 일반 일정표와 현재 사용 판정의 근거가 된다. 일반 신규 확인의 메모는 선택이며 충돌 재확인에는 근거 메모가 필요하다. 문서 확인은 실제 확인한 원문 버전을 연결하고 종이·오프라인 자료 확인도 별도로 보관한다. 확인일을 모르는 기록도 저장하지만 관리 기록에만 둔다. 입력일을 확인일로 채우지 않는다. 월 단위 직접 확인은 월 계획으로 보관하고 일 단위 확인율에는 넣지 않는다.

값 비워 두기, 명시적 삭제, 자동값 사용으로 되돌리기를 서로 다른 동작으로 제공한다. 날짜를 바꾸면 기존 시간의 날짜 연결을 다시 확인한다. 수기값과 새 공식 근거가 충돌하면 수기 원본을 보존하면서 해당 필드를 보류한다. 시간만 충돌하면 확인된 날짜는 제공한다. 행사 식별이나 취소 여부의 미해결 문제는 행사 전체에 영향을 준다.

`알림 읽음`은 게시 재개나 충돌 해결이 아니다. `직접 다시 확인`은 실제 확인 방법·시점·근거 메모와 현재 충돌 fingerprint에 연결하고, `검증된 새 값 적용`은 검증을 통과한 새 근거를 사용한다. 동일한 내용의 원문을 다시 조회한 것만으로 해결된 충돌을 되살리지 않는다. 새로운 충돌이 생기면 다시 확인한다. 기관 연락처의 사용자 정정도 목록 갱신으로 덮어쓰지 않으며 운영 중단·취소 주의는 감추지 않는다.

## 6 전체 목록, 지표와 HTML

유형별 공식 목록의 출처, 기준일, 지역 범위, 완전성, 수록 수와 DB 연결 수를 보여 준다. 전체 건수를 알 수 없으면 누락 여부 미상으로 표시하고 임의의 100%를 만들지 않는다. 목록에서 빠졌다는 이유만으로 기관을 자동 삭제하거나 폐원 처리하지 않는다. 운영 종료가 공식 확인되고 종료일이 행사일 이전 또는 당일이면 해당 예정 행사를 제외하지만 종료일 미상은 확인 대상으로 남긴다.

조사 완료와 사실 확인을 구분한다. 날짜 확인 기관 수는 현재 일 단위 날짜 사용이 허용된 고유 기관 수다. 시간 확인 기관 수는 같은 행사·날짜의 현재 시작 시간 사용까지 허용된 고유 기관 수다. 월 계획, 과거 확인값만 남은 항목과 보류 후보를 확인율에 넣지 않는다. 날짜만 확인된 기관은 날짜 지표에는 포함될 수 있어도 판매 준비 목록에는 들어가지 않는다. 분모는 시즌의 대상 등록 기관이며 0이면 비율은 null이다. 복수 행사를 기관 수로 중복 집계하지 않는다. 목록이 불완전하면 `등록 기관 기준`이라고 표시한다.

데이터는 SQLite에 저장한다. 읽기용 HTML은 같은 snapshot·revision·정책의 Publication으로 일반 일정표, 판매 준비 필터와 확인할 목록을 만든다. 일반 일정표의 과거 확인값에는 재확인 상태를 함께 넣는다. 원문 전문·API 키·사적 메모는 기본 제외하고 `내 메모 포함`도 기본 꺼짐이다. 월 계획과 후보는 확정 일자로 섞지 않는다. 화면 필터와 무관하게 기본 내보내기는 해당 시즌 전체를 담는다. 외부 CDN 없이 오프라인 검색·필터와 인쇄를 지원하며 출처 열기에는 인터넷이 필요하다. HTML은 생성시점 사본으로 자동 최신화되지 않는다.

| P0 검증·설명 | 계약/반례/정상 예제와 실제 기관 종단 시험, 실행 안내 | 기능·기술·한계의 검증 근거. 발표 자료와 연습은 별도 |
| 조건부 확장 | 격리 브라우저, HWP 미리보기/전체 파서, HWPX/OCR, 이미지 후보 | 대표 기관 조사에서 병목과 개선 효과가 확인된 것부터 추가 |
| P1·P2 | 목록 자동 동기화 확대, 일괄 메모, CSV, SSE, Windows 패키징, 예약·알림·복원 UI | 핵심 흐름 통과 후 실제 사용 환경에서 별도 검증 |

P0 기본 reader는 HTML과 텍스트 PDF다. 브라우저/HWP/이미지 후보는 기본 비활성이며 반드시 제공할 P0 기능으로 간주하지 않는다. 전체 목록 확보 자체를 확장으로 미루지는 않는다. 특정 형식 때문에 대표 기관에서 필요한 정보가 막히면 그 도구를 앞당기되 게시 조건을 낮추지 않는다.

사용자가 `.env`에 준비하는 것은 NEIS·검색 API 키와 선택한 모델의 연결 정보다. 시간·동시 처리·재시도 한도와 선택 기능의 기본값은 설정 파일에서 관리한다. 특정 키가 없으면 해당 연결의 제한을 표시하되 저장 조회·수기 입력과 독립적으로 가능한 기능은 사용할 수 있어야 한다.

P0에는 선택한 모델 백엔드 하나를 사용한다. 초기값은 Ollama이며 `.env`의 `LLM_BACKEND`를 `openai`로 바꾸고 자신의 API 키를 입력하면 OpenAI를 선택한다. 선택한 백엔드만 준비 상태를 검사하며 OpenAI 선택에 Ollama 실행을 요구하지 않는다. OpenAI 선택은 공개 문서의 필요한 텍스트 구간 전송을 허용하는 선택이고, 이미지·사적 수기 메모는 포함하지 않는다. 명시적인 전송 금지와 실행환경 조건은 계속 적용한다. 기존 Ollama 모델명과 OpenAI 기본 모델은 시작 설정이며 정확성 우위나 실제 PC 성능의 증거가 아니다. 장애 시 다른 백엔드나 demo로 자동 전환하지 않는다. 초기 운영 자동 규칙 허용 목록은 비어 있고, 정상 통과와 반례 차단을 확인한 규칙만 활성화한다.

구현 순서는 게시 판정·반례 검사, 계약 정합성, 정형 처리부터의 최소 종단 흐름, 실제 대표 기관 시험, 필요한 도구 확장이다. 이후 전체 큐·수기 보호·재시작·HTML을 통합 검증한다. 기능 완료, 자료원 실연동 완료와 전체 목록 확보 완료를 별도로 보고한다. 모든 일정이 공개되는 것을 완료 조건으로 삼지는 않지만, 미해결 기관을 정확히 남기는 동작은 필수다.

## 8 현재 상태와 남는 한계

이 인계물은 기획·설계·계약과 실행 가능한 참조 검사다. 실제 FastAPI 앱이나 전체 Agent의 구현 완료를 뜻하지 않는다. 과거 probe에서는 개별 읽기와 모델 호출을 실행했지만 잘못된 기관·연도·정밀도·시각 생성·다른 행사 선택·합성 인용 오류가 있었다. 제공된 증거 수준과 검증 범위는 실행 근거 문서에 구분한다.

공개정보 부재, 원문 자체의 오기, 전화 확인 착오와 사후 변경은 없어지지 않는다. 보수적인 현재 사용 보류는 맞는 일정도 일시적으로 판매 목록에서 제외할 수 있고, 일반 조회의 과거 값도 최신 사실 보장은 아니다. 확인 방법·시점·읽기 범위와 미해결 사유를 드러낸다. 고정 반례의 차단을 전체 기관 무오류나 완전 위임 보장으로 확대하지 않는다.

벡터 DB, 별도 Supervisor, Redis, 다중 서버, 수량 예측·판매 위치 추천·전국 확대는 이번 핵심 요구가 아니다. PPT와 발표 준비, Before/After 보너스 비교는 개발 완료 조건에서 제외한다.
